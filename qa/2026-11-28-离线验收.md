两个 Linux 客体以普通用户运行同一安装入口，覆盖首次部署、缓存复用、真实中英文 OCR、出带来源批注的草稿、任务查询、并发修复和错误返回。本地客体没有安装 LibreOffice。GitHub Actions 在两种原生 Linux CPU 上另行构建，覆盖安装了 LibreOffice 的断网用例。CI 使用本机编译的 OCR 并单独记录摘要。[原生 Linux 工作流](https://github.com/QingNagi/skill_for_integrator/actions/runs/46061312120)

Windows 验收使用发起任务的工作目录作为输出根目录。两个办公后端分别完成草稿、审核、定稿、DOCX → DOC → DOCX 和 PDF 导出。在 TEMP/TMP 指向无效路径时，往返文件保留两条批注和数值 17.8。核对 DOCX 应用属性、PDF 生成器和来源文件摘要，确认两个办公软件都实际写出了文件。此轮桌面验收覆盖 Word 2010 与指定 LibreOffice 版本。

本地 QEMU 每个架构运行了 3 次冷启动、5 次热启动。x86_64 完整草稿任务中位数为 42.04 秒和 6.17 秒，ARM64 为 40.30 秒和 6.13 秒。软件模拟的耗时不能代表原生机器。

旧版 Word 的真实样本另暴露出后台打开旧 DOC 超时的问题。合格的本地 Word 97+ 文档现在由已注册的 Word 2010 转换器优先处理，受限制来源或存在文件阻止策略时交由 Office 判定。两份旧文件的独立转换总计约 0.30 秒，生成的 DOCX 均可回读。

## PDF 和业务结果

- 固定三份 PDF，新旧后端均读出 7 页。两份含表格的业务 PDF 共 7 张表，450 个单元格的位置、跨行跨列范围和去除空白后的文本全部一致。一页原生文字减少的 14 个字符已存在于对应的三个表格单元格中。

- 扫描样例中的 24 °C、55% 和测点编号均可从原页回读。初版固定放大到 300 DPI 曾把 55% 读为 95%，按实际像素限制渲染分辨率后读回 55%。扫描标题仍有一字误读。TSV 词置信度低于 80 的数字显示复核标志；高分数字仍须核对原图。

- 合成模板的 8 个已知填表位置全部正确，核验了 14 条来源链接，包括 6 个 Word 书签和 8 个 Excel 区域。手工修改和审核人批注保留到终稿；未确认的 OCR 来源会拦截定稿。可运行 `python qa/generate_pdf_examples.py <新目录>` 生成合并表头、扫描页和图文混排页练习。生成图像样例的测试环境需有 Pillow。

- 两份真实任务均有需要用户确认的项目，分别为 7 项和 3 项。记录任务的 96 个 Excel 计划值逐项回读引用区域，84 个数值或范围和 12 个 PASSED 判定均与所引用单元格一致。与提供的旧成品对齐后，13 项文字相同、5 项数值等价、78 项不同。该检查尚不能确认所选样品对应同一批次。章节案例有 5 段摘录与旧成品未逐段完全匹配，且有来源缺失。两案都保留计划并等待确认，原件摘要未变。

直接调用精简构建的 Tesseract 执行 `--list-langs` 时，会在标准错误输出一组 Leptonica 内部 TIFF 字体图像诊断。该命令退出码为 0，列出 chi_sim 和 eng 两个模型。技能通过 PDFium 渲染并向识别器传入 PNM 图像，中英文实样另行验证。

## 完整任务耗时

Windows 的计时从调用完整包 run.cmd 开始，到草稿、快照和报告写出结束。同一条命令完成任务并核验四条批注和两条来源链接。新缓存首次 12.68 秒；同版本连续三次复用分别为 1.78、1.77、1.42 秒，中位数 1.77 秒。安装自检仅在首次出现。同一文件重复解析可复用项目缓存。

本机 Claude Code 使用虚构资料，明确路径的一次任务耗时 20.70 秒，共 2 次工具调用，生成一份草稿、快照和报告。两个同名来源的用例耗时 7.96 秒，列出两条候选路径供用户选择，未生成草稿。这是指定模型、机器和样例的一次观察；无技能对照受命令权限影响，因此未计算相对加速倍数。
