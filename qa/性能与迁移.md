# doc-integrator 性能与新环境验收

## 从请求到交付草稿

2026-11-27，使用同一组合成 Word 模板、任务书、提示词与工具权限，本机 Claude Code 2.1.316 分别用旧版 `684ae4b` 和新版执行了三次任务。每次从用户发出请求开始计时，直到 Agent 返回可供审核的草稿、来源快照、报告及三类缺口数量。模型后端为 `deepseek-flash[1m]`，两组均从项目源码入口启动。这里的耗时包含模型服务响应时间。

| 三次独立任务 | 旧版 | 新版 |
|---|---|---|
| 完整交付耗时 | 35.936、30.389、26.865 秒 | 14.974、12.669、8.971 秒 |
| 中位耗时 | 30.389 秒 | 12.669 秒 |
| 本地工具调用 | 12、12、9 次 | 1、1、1 次 |

新版在一次 `run --draft` 中复用建任务时读取的文档与本次规划，交付时返回需要报告的路径、来源摘要和缺口数量。三个案例都保留了两节逐字相同的正文、4 条批注、2 条链接及其对应的快照书签。样本为给全路径、来源明确的摘抄任务。遇到缺件、来源不明、待核 OCR 或无法定位填写位置时，会停下来澄清；确认定稿是另一次用户操作。

Windows 完整离线包另用同一对虚构文件运行。每版用了三个空用户缓存，每次首次任务后再建一个新任务。旧流程依次执行 `run`、`show`、`draft`，新流程调用 `run --draft`；第二个交付点均执行相同的 `final`。表中为三次的中位耗时，包含启动器与文件写入。“至终稿”假定测试审核人立即确认。用户实际审阅用时另计。

| Windows 项目入口到可用文件 | 旧包 | 新包 |
|---|---|---|
| 空缓存到审核草稿（含首次自动部署及双语 OCR 自检） | 6.309 秒 | 4.447 秒 |
| 同版第二次任务到审核草稿 | 2.857 秒 | 1.078 秒 |
| 空缓存到确认后的终稿 | 7.398 秒 | 5.476 秒 |
| 同版第二次任务到确认后的终稿 | 3.945 秒 | 2.080 秒 |

12 次交付中，草稿正文 XML 均逐字节相同，终稿正文 XML 也逐字节相同。草稿有 4 条批注，终稿保留 2 条模板批注。温启动均未重装。最终包另通过嵌入 Python 的 172 项测试，电特性实测表的 8 个数值、两个摘抄章节与上一版结果一致，扫描件与同名来源均在需要确认处暂停。

原生 Ubuntu 24.04 x86_64 和 aarch64 分别在断网命名空间内完成了从可读模板到带来源批注草稿的交付。使用已装的 LibreOffice Writer，两个平台还实际导出了 PDF，并在 TEMP、TMP 和 TMPDIR 都指向普通文件时完成 DOCX→DOC→DOCX 往返，读数 `17.8 V` 得到保留。x86_64 首次部署至草稿和同版第二次任务的中位耗时为 3.115 秒、0.363 秒，aarch64 为 2.934 秒、0.428 秒。CI 预备宿主时安装 Writer，实际文档任务全程断网。[原生双架构运行记录](https://github.com/QingNagi/skill_for_integrator/actions/runs/46021539229)

## Windows 工作文件

正式包在本机 Word 2010 上用一个普通文件模拟损坏的 `TEMP` 与 `TMP`，成功将 DOCX 转为二进制 DOC，并从 DOC 导出可提取标题的一页 PDF。同一测试里，PowerShell 7 初始化自己的 Temp 驱动器时可能输出路径提示。Office 转换使用任务自己的临时目录。

D 盘旧部署的低完整性进程仍受操作系统的缓存权限约束。在该进程中，本机 Office 自带的 Wordconv 能把本地旧 DOC 读为 DOCX；加粗的中文标题、3×2 个表格单元格、单位和负号与 Word 2010 回读结果一致。完整样例还验证了带批注的旧档模板能交付新草稿。Wordconv 支持本次读取方向。DOC、PDF 导出依赖可用的 Word、WPS 或 LibreOffice。来源保护、Office 拒绝打开和当前用户无权写入输出目录的情况，按实际错误处理。

## 前一轮分项测量

2026-11-27，比较上一版 `b354c7d` 与本轮优化。Windows 使用同一台 x64 机器、同一批虚构文件和独立应用缓存。首次安装测试保留正常的操作系统磁盘缓存。计时覆盖脚本实际运行时间，未计入模型思考时间。

## 换机器时会遇到什么

| 场景 | 复测结果 |
|---|---|
| 没装系统 Python 或 OCR | 从空应用缓存运行，使用套装自带的 Python、PDF 库和中英文模型。扫描案例正确回读第 1 页的温度、湿度及测点编号，并在缺少依据时等待用户确认。 |
| 用户已设置 `DI_OCR=off` 或 `DI_NO_VENDOR=1` | Windows 首次自检会验证随包组件；实际任务尊重原有设置。用户关闭 OCR 后，扫描件识别能力仍会受限。 |
| 启动时缺少业务 Python 模块 | 两种系统会检查打包时实际包含的模块。保留原始载荷时可恢复缺失文件，现有自定义规则和排版配置在恢复中保留。 |
| Windows 修复后提示临时文件被占用 | 用真实文件句柄模拟占用，0.8 秒的占用解除后可自动完成清理。5 秒的持续占用超过有限重试窗口时会报告拒绝访问；待占用解除后可重试。 |
| Windows 报 Word 无法创建工作文件 | 这一轮旧包的预检识别到了不可写的 TEMP 或 Content.Word。新版在上述“Windows 工作文件”验收中覆盖了这两种情况。 |
| 目录内有同名来件 | 精确查找列出每个路径。在本机 Claude Code 实测中，助手列出甲、乙两个来源并等待选择。自动命名的同名模板任务即使在同一秒创建也得到不同的任务目录。 |
| 来源目录含分号或模板名含方括号 | 对已存在的路径按字面值处理。批量清单可往返保存包含分号的来源。批量目标没有匹配项会返回错误，保留已有清单。 |
| 输入损坏后用原任务名重试 | 所有输入成功解析后才写入任务信息。修正损坏来件后可重试；已存在的同名显式任务仍受保护。 |
| 输入位于别处，工作区是新目录 | 草稿和审核报告在发起任务的工作目录下的 `整合输出/`。用 `--out` 可以指定其他可写目录。 |

精度核对覆盖了电特性表的 8 个实测单元格、章节正文与批注链接、OCR 页码和人工待答项。最终交付仍取决于实际提供的来源；缺少的章节或测量记录须由用户补充。旧格式转换和 PDF 导出依赖目标机已有的办公软件。发布评审状态见同目录的 [Tier 1 复核说明](README.md)。
