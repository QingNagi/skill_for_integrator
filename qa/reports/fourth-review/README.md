# 溯源填写助手 1.3.0 综合验收

使用本机 Claude Code 和已配置的 DeepSeek，从独立项目中的合成来件生成 Word 文件。每个会话结束后，用项目外封存的答案读取实际 DOCX 逐格计分。人工回复由评测程序按模型实际问到的问题给出。重复同一题时，报告分别列出运行次数与不同判分位置数。

最终包的 30 次真实 Claude 尝试中，2 次摘抄完整交付；其余 28 次被已配置的 DeepSeek 服务以 HTTP 402（余额不足）中断，其中普通用例 13 次、交接 5 次、变体 10 次。各次中断均保留原始回执。回放复用了输入与审核决定，并重新生成 Word；它能验证写入及判分的一致性。最终包的整批 Claude 耗时、调用 P90 和模型交接完成率仍待额度恢复后实测。[普通会话](claude-runs.json) · [变体与重放](variants.md) · [交接与实物比对](handoff.md)

**整项任务的耗时。** 第五候选的同一五模板任务，普通对话全程中位数 271.73 秒、63 次工具调用，最慢 488.95 秒。独立交接全程中位数 156.96 秒（含拒绝测试及模拟终端确认），其中规划中位数 149.13 秒、30 次工具调用，独立出稿为 4.41 秒。两组各跑 5 次，真人阅读耗时另计。普通对话出稿后分别又调用 3、56、33、23、20 次，P90 为 56。交接模式把写入、结构自检、来源核对和交付清单交给本地程序，原规划进程在出稿后的调用均为零。继续优化普通对话时，可从重复查看目录、检查已交付文件、再次查提纲和重复提交段序选择入手。

**新的 Windows 环境。** 旧包能复现在 D 盘中文项目首次安装时无法创建临时文件。最终包在可写缓存中做双语自检，重复启动复用已安装环境。发布目录暂时被占用时会有限重试。另用同一份两页 PDF、三组互相独立的空缓存验证实际读取：默认临时目录、三个临时变量指向普通文件、显式可写目录，均保留原生数字 4.75 V，并识别第 2 页的中文及英文，未读页为零。Windows 全依赖单测 400/400；无 OCR 的 Linux x86_64 单测发现 400 项，369 项通过、31 项按环境跳过、零失败。Word 2010 和隔离的 LibreOffice 26.8.3.1 均完成原生编辑、带 3 条批注的 DOC 往返及单页 PDF 导出。[平台记录](platform.json)

在没有网卡的 Linux 虚拟机中，x86_64 和 aarch64 均以普通用户完成完整包与双包安装、中文与英文 OCR、复用运行时及独立终端出稿。两个系统的 glibc 均为 2.36，虚拟机没有安装 LibreOffice，旧格式转换的实测来自 Windows 上的两套办公软件。[虚拟机与 Office 记录](platform.json)

## 交接出稿与普通对话

普通对话中，交付清单能减少必要的回读，模型仍能继续查看文件。第四候选的五模板每次均有正确清单，出稿后工具调用为 6、9、6、15、18 次。两套变体各有 33 个不同判分位置，十次全部正确，只有三次满足末版出稿后最多五次调用。摘抄的五次结果为 3、1、2、1、1 次。[变体记录](variants.md)

需要控制出稿后的调用次数时，Claude 完成规划、封存并退出。审核人在另一个终端打开本批脚本，由同一个 `di.py deliver` 完成确认、写入与自检。第四候选五次交接均在原规划进程退出后出稿，每次 200/200，五份 DOCX 与普通模式的 480 个表格位置逐一相同。规划工具调用中位数 32，独立出稿中位数 3.762 秒。第 5 次会话封存后仍操作了 25 次才退出，说明整项任务的主要时间仍在规划。独立终端的审核输入由测试程序模拟。[逐次交接与计时](handoff.md)
