## 实际由 Claude Code 完成的任务

测试使用本机 Claude Code 的 DeepSeek 配置，stream-json 记录的模型为 `deepseek-flash[1m]`。每次从独立项目、冷应用缓存开始，复制技能及题目指定的输入，未给模型评分器、预期值或参考成品。多轮任务中，测试程序扮演虚构审核人，在收到对应问题后才交付既有预设答复和程序清单。用例要求审核草稿，故保留来源快照和批注。模型两轮之间的等待、外部判分及人工阅读时间不计入运行耗时。

| 金标 | 独立核对 Claude 实际交付的结果 |
|---|---|
| 验证记录，163 格 | 131 格正确填入，26 格正确留空，5 格保持原样，1 可选项符合；错填、误填、误改、修约掩盖超限、超限格漏警均为 0。三件输入摘要未变，程序清单摘要与审核记录一致。 |
| 文档摘抄，24 项 | 9 项必含内容、7 个表格行、1 项顺序、7 项禁含内容均通过。检查了 Word 批注内的两条链接和所指文件，模板与两份来源的摘要未变。 |

外部样例封存清单的 5 项摘要在判分时均匹配。签署栏为空。上述两份模板与项目自带的五份教学模板分别计数。尚无 5 份模板、至少 200 个真实业务单元格、由独立人员签名封存的结果。

### 过程和耗时

三次运行采用相同的入口任务及审核口径，每次新建项目和应用缓存。记录表在每次收到 Claude 的问题后才提供对应回复，三次均为 4 轮；摘抄每次为 1 轮。每种条件各测一次，模型的工具选择和耗时会波动。

| 运行 | 验证记录，秒 / 工具调用 | 摘抄，秒 / 工具调用 | 两份交付物的判分 |
|---|---:|---:|---|
| Windows 候选包 `206e6b5d…` | 251.68 / 60 | 90.55 / 23 | 163/163、24/24 |
| 1.1.1，增加明确下一步及空脚注识别 | 148.15 / 22 | 21.04 / 6 | 163/163、24/24 |
| 最终 1.1.2，缓存共享冲突修复 | 178.12 / 21 | 24.94 / 8 | 163/163、24/24 |

最终记录任务没有权限拒绝，输入、缓存读取和输出分别为 46,658、678,912、33,258 token。最后一轮交付占 135.19 秒、17 次工具调用；过程中试图从离线环境导入额外的工作簿库，还生成了临时检查脚本。原始 XLSX 可直接交给 `answer --evidence`。一次提交所有已获授权、当前可见的问题仍有提速空间。对已确定超限的样品保留了回读两段原始单元格的必要步骤。最终摘抄第 6 次调用生成草稿，之后又读了一次审核报告和命令参考。

- 首轮需要用户确认型号时，模型曾继续读整张表、检查原始 ZIP 和 Python 环境，做了 21 次工具调用。机器输出现在给出 `next_action=ask_user`。对已结构核对且没有未读、未核或警告的草稿，输出 `deliver_draft`。
- 控制用脚注和尾注分隔条在这批 DOCX 中共占 8 个部件，里面没有业务文字。修复前单个摘抄任务因此得到 4 条误报。新的内容缓存版本区分空分隔条与真实脚注、图形、域及无法识别的 XML。
- 将一次人工决定和多项清单证据一同提交。文件证据只归到对应问题。带证据的回答保存文件 SHA-256，按单一工作簿、工作表、标签列和已选工况核对来源。新增章节在 Word 批注和审核报告中都能追到具体来源。
- 最初的 163 格底层对照只有 20 个必填值正确，曾将一项超限值显示为限值。修复后，IOS 第 3 个样品的原始上端点 −3.996 mA 明确标为超出上限 −4 mA；IOZ 的 10.4 µA 也保留警告。清单证明了供电电压，但未证明的负载和其他附加条件仍阻止总体合格和默认定稿。
- 五个合成批次的另一场 Claude 验收，题面提到采集说明，却只提供规范与无单位的原始测量表。Claude 生成了 5 份草稿；130 个应空格处理正确，70 个预期填写格留空，错填 0。程序检测还发现 Claude 只把第一句任务要求传给了技能。补交一份含单位和标称供电的采集说明后，原会话再次交付的 5 份草稿全部通过，70 格正确填写、130 格正确留空。另一场 1.1.1 空目录测试首轮仅出计划，即使材料齐全，仍多问了一轮；重申已有决定后，200 格全对，共 249.38 秒、60 次工具调用。评分与现场提供的证据范围必须一起阅读。

### 五组批量给件的实际表现

在 1.1.2 的空项目中交付五组三件输入及可直接导入的采集 CSV。Claude 在一个会话、一个用户轮次内交付 5 份具名任务，分别为 40/40，合计 70 个正确值和 130 个正确空格。按最终回复指定的五份 Word 评分，各自的三件来件配对、批注快照链接、报告和结构检查均通过。五组共用 324.71 秒、110 次工具动作，出现 7 次权限拒绝。输入、缓存读取和输出分别为 103,804、7,166,464 和 51,873 token。

**批量流程仍有冗余。** 第 78 次调用时五份交付草稿均已生成，之后又用 32 次调用检查文件和格式。项目中多出一份早期草稿和三个临时核对任务。完整任务耗时也受模型上下文和重复读取的影响。进一步优化优先考虑让批量入口一次返回各任务的最终路径、来源配对、结构状态及须人工复核的例外，让 Agent 只打开有疑问的原始范围。对多批共享决定仍应按批号确认适用范围。该改进尚未作为本轮已验证能力。

从仓库运行 `python qa/accuracy_suite.py generate <新目录>` 可生成五组教学模板、原始工作簿、规范及 `本批采集说明.csv`。把五个示例目录和 CSV 交给模型即可，`expected.json` 和 `expected.sha256` 由测试人放在工作区外。CSV 含 15 条仪器元数据，无测量结果或目标答案。

另做了同名选源、缺件后补件、按批注修订、定位章节四种任务的有无技能对照。对照组也交付了同名来源的正确正文，Word 中缺少定位到来源快照的原生链接。[对照实验及 token 统计](agent-timings.md)

## 原始业务记录的 78 项差异

96 个历史位置中，13 个显示文本相同，5 个数值等价，另有 78 个不同。逐格复算能重现旧计划的 78 个显示值。旧成品含数值的 72 格均未在当前工作簿找到同一参数、同一条件、同一样品且两端都精确相等的整组原始读数。另外 6 格旧成品写的是判定。旧成品和所给规范的型号不同，目录中未找到可独立证实原批归属的 A.xlsx 或适用性记录。

| 涉及格数 | 差异原因 | 现有依据能判定的范围 |
|---:|---|---|
| 30 | 无电压后缀，其中 6 格共用 IIH/IIL 标签 | 符号和数值可追溯。实际供电、单位、共用段归属仍须证明。 |
| 3 | 中间电压，单一参数 | 原表能复算。同批身份、单位和试验设置确认后才适用于该记录。 |
| 30 | 中间电压，复合标签，其中 3 格含别名 | 不能从词序或数值落在限内推出段序。核对程序清单的分段和别名。 |
| 6 | 高低阈值 | 高阈值结果与旧判定相容。低阈值的符号和数据定义关系未证实。 |
| 6 | 抖动标签有三个参数、两个段 | 两个段的参数归属需要原测试程序。 |
| 3 | 数据率原始数列全为 1 | 规范下限 800 Mbps 单独不能证明本次实测速率。 |

在未提供新业务证明的真实记录中，型号冲突停在首个适用性问题，准确覆盖 144 个规范字段和 96 个实测候选。实际写入为 0。合成样例的回答仅对相应合成任务有效。[上一轮原件核对及对照口径](../../2026-11-28-数据核对与全流程复验.md)

## 复现

仓库自带的五个参数排列用例可在项目外重新生成。预期文件在执行前封存。下面最后一条运行的是显式模拟审核人的 CLI 对照组。真正的 Agent 验收可用会话驱动程序，每轮传入测试人的原话文件，再单独评分。

```text
python -m unittest discover -s tests
python -m unittest discover -s qa -p "test_*.py"
python qa/accuracy_suite.py --help
python qa/run_accuracy_suite.py <离线包入口> <封存样例目录> <新输出目录>
python qa/claude_review_turn.py <隔离项目> <项目外的日志目录> <项目外的本轮用户原话.txt>
```

## 验收边界

- Windows 实机覆盖 Microsoft Word 2010、Excel 2010 及隔离的 LibreOffice；新式批注的回复和解决状态另有 OOXML 回归。Word 2016 及以上版本和 WPS 的真实交互须有相应安装环境。旧格式和 PDF 导出使用目标机已有办公软件。
- 发布资格以官方扫描器的原始报告为准。源码、精简包和完整包有独立的发现清单；原生运行时另有 SBOM、上游依赖哈希和 OSV 查询。未代表发布者授予项目许可、签名或新风险豁免。
- 同一 PDF 重复图像已有 OCR 缓存。跨任务并行出稿已实现。单份 PDF 内多进程 OCR、跨任务共享 Office 实例、真实扫描件上 tessdata_best/RapidOCR 的对比、企业 AppLocker/WDAC 实机签名白名单及真人确认时长尚无本轮验收。
